# Repository Guidelines

## Project Structure & Module Organization
The Vite-powered Vue app boots from `src/main.js`, global CSS lives in `src/style.css`, and routing is configured under `src/router/index.js`. Views stay inside `src/views`, while reusable UI sits in `src/components` and shared logic in `src/composables`. Use fixtures from `src/data` to keep demos deterministic and drop static media into `src/assets`. Prefer the `@/` alias (for example `@/components/ImpactStats.vue`) so refactors do not break imports. Specs live next to their components or under `src/__tests__/`. Files under `public/` publish verbatim; never edit `dist/` because it is regenerated by Vite.

## Build, Test, and Development Commands
- `npm install` syncs dependencies after updating `package*.json`.
- `npm run dev` launches the Vite dev server; pass `-- --host` for LAN testing.
- `npm run build` compiles an optimized bundle and surfaces syntax/type regressions.
- `npm run preview` serves the latest build artifact for stakeholder smoke tests.
- `npx vitest` or `npx vitest run --coverage` runs the suite interactively or in CI with coverage output.

## Coding Style & Naming Conventions
Single File Components use `<script setup>`, two-space indentation, and single quotes. Components stay PascalCase (`WaterHero.vue`), composables use camelCase prefixed with `use` (`useImpactStats`), and route names mirror the lowercase URL slug. Keep shared or responsive CSS in `src/style.css`, while component-specific rules should be scoped locally. Prefer declarative props, avoid mutating incoming data, and extract repeated logic into helper composables.

## Testing Guidelines
Vitest plus Vue Test Utils drive CI. Co-locate focused specs beside their component (e.g., `ImpactStats.spec.js`) and reserve `src/__tests__/` for broader flows or router hooks. Target ≥80% coverage on shared utilities, lean on fixtures from `src/data`, and stub network calls. Run `npx vitest` during development and enforce `npx vitest run --coverage` before a release branch is merged.

## Commit & Pull Request Guidelines
Follow Conventional Commits such as `feat: add donation CTA` or `fix: correct hero contrast`, and keep each commit scoped to related files. Pull requests should describe context, link issues, include screenshots or recordings for UI changes, and document evidence that `npm run build` plus the full Vitest suite passed. Mention any new environment variables with purpose, defaults, and rollout notes.

## Security & Configuration Tips
Never commit credentials or API tokens. Store secrets inside `.env.local` (already git-ignored) and access them through `import.meta.env`. If a secret leaks, rotate it immediately, scrub references from history, and describe the mitigation steps in the release notes.
